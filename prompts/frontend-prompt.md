# Промпт для AI: frontend игры «Собиратели нелепых артефактов»

Ты — senior frontend-разработчик с опытом браузерных 2D-игр. Твоя задача — **изучить существующий проект в `./frontend` и полностью реализовать frontend** сетевого платформера «Собиратели нелепых артефактов».

Не ограничивайся советами и псевдокодом: после аудита проекта внеси рабочие изменения, установи только действительно нужные зависимости, запусти линтер, тесты и production build. Не меняй `./backend`.

## Обязательный аудит перед реализацией

1. Изучи дерево `./frontend`, `package.json`, lock-файл, TypeScript-конфигурацию, bundler, UI-framework, роутинг, state management, тесты и уже установленные игровые/графические библиотеки.
2. Проверь, есть ли Phaser, PixiJS, Excalibur, Kontra, Matter, Canvas-обертка или собственный renderer.
3. Если подходящая библиотека уже используется, продолжай с ней и не создавай параллельный renderer.
4. Если игровой библиотеки нет, по умолчанию выбери **Phaser 3** как renderer/scene/camera layer, если он не конфликтует с текущим стеком. DOM-framework, если он уже есть, используй для экранов входа, HUD и результатов; игровой canvas интегрируй как изолированный компонент.
5. Не добавляй тяжелый physics engine ради MVP: authoritative physics находится на backend. Клиентская физика нужна только для ограниченного prediction локального игрока.
6. Кратко зафиксируй найденные зависимости и объясни выбор renderer до внесения основных изменений.
7. Не останавливайся ради уточняющих вопросов: разумные решения принимай самостоятельно и документируй.

## Цель

До четырех активных игроков появляются в разных углах большой платформенной карты. Каждый пользователь задает имя при входе. Игроки перемещаются, прыгают, собирают нелепые артефакты, атакуют друг друга и ходящих монстров.

Первый игрок, которому сервер подтвердил сбор пяти артефактов, побеждает. Игрок с нулевым HP больше не участвует до следующего раунда и смотрит игру как spectator. После экрана результатов backend выбирает новую случайную карту, назначает активные места и начинает новый раунд.

Если активных мест уже четыре или пользователь подключился посреди текущего раунда, он наблюдает и ждет следующего раунда. Очередью и ролями управляет только backend.

## Художественное направление

Стиль: яркое комедийное абсурдное фэнтези — «Собиратели нелепых артефактов».

Персонажи могут выглядеть как разноцветные гоблины-археологи, еноты-воры, ведьмы-стажеры и рыцари, потерявшие замок. Для MVP допустим один нейтральный sprite с четырьмя хорошо различимыми палитрами, но архитектура должна позволять заменить его отдельными персонажами.

Артефакты имеют разные иконки, но одинаковую игровую ценность:

- левый ботинок великана;
- зуб дракона с пломбой;
- пузырек с понедельником;
- карта, ведущая не туда;
- золотая пуговица короля;
- говорящий камень;
- ложка, которая боится супа;
- сертификат на владение облаком.

Монстры:

- ворчливый гриб;
- сундук-самозванец.

Если готовых ассетов в проекте нет, используй аккуратные временные примитивы, простые локальные SVG/shape assets или разрешенные существующие assets. Не блокируй функциональность отсутствием финальной графики и не подтягивай случайные изображения из интернета.

## Источник истины

Backend авторитетен. Frontend:

- отправляет input, но не отправляет координаты, HP, урон, количество артефактов или победителя;
- принимает map definition, snapshots и события;
- не объявляет победу до `round.finished`;
- не рассчитывает фактическое попадание атаки;
- не назначает себе роль active/spectator;
- хранит session token только для reconnect и не выводит его в логи.

Поддержи версию WebSocket-протокола, `roundID`, `serverTick` и input sequence number. Не смешивай network DTO с view model: добавь явный слой преобразования и валидацию входящих сообщений.

## Главная оптимизация: viewport windowing

Карты значительно больше экрана. **Запрещено каждый кадр рисовать всю карту и все объекты мира.** Под словом windowing имеется в виду camera viewport/culling, а не создание нескольких окон браузера.

Реализуй:

- логический world полного размера;
- camera viewport, следующий за локальным игроком;
- ограничение камеры world bounds;
- render window, равное видимой области камеры плюс небольшой overscan, например один spatial chunk или 15–25% размера viewport;
- spatial chunking статической геометрии, ориентир `512 × 512` world units, либо нативный tilemap/camera culling выбранной библиотеки;
- создание/активацию визуальных объектов платформ только для chunks, пересекающих render window;
- culling игроков, монстров, артефактов, эффектов и подписей вне render window;
- сохранение сетевого состояния offscreen-сущностей без их дорогостоящей отрисовки и анимации;
- корректное появление объектов при входе в viewport без заметного popping за счет overscan;
- отдельный HUD, который не движется вместе с world camera;
- debug-режим, показывающий viewport, overscan, активные chunks, FPS и число отрисовываемых объектов.

Если используется Phaser Tilemap, задействуй camera/tile culling и не включай `skipCull` без измеримой причины. Если карта строится из прямоугольников платформ, создай простой spatial index/chunk registry и активируй только видимые chunks. Если используется PixiJS, применяй встроенный/официальный culling-механизм актуальной версии либо собственную проверку world bounds, а не только смещение общего контейнера.

Не удаляй offscreen-сущности из client state: windowing относится к render/update cost, а не к получению authoritative snapshots.

## Экраны и состояния UI

### Экран подключения

- Поле имени с ограничением 1–16 символов и понятной клиентской валидацией.
- Кнопка подключения.
- Индикатор соединения и понятные ошибки: некорректное имя, имя занято, несовместимая версия протокола, сервер недоступен.
- При наличии действующего session token сначала попытка resume; если она отклонена, обычное подключение.

### Ожидание и countdown

- Текущая роль: active или spectator.
- Для зрителя — номер в очереди.
- Список до четырех участников следующего/текущего раунда.
- Название выбранной карты.
- Большой countdown без возможности управления.

### Игровой HUD

- Номер раунда и оставшееся время.
- Для каждого активного игрока: имя, цвет, HP, артефакты `N/5`, состояние alive/dead/disconnected.
- Локальный игрок визуально выделен.
- Краткие feed-сообщения: сбор артефакта, попадание, смерть, убийство монстра.
- Индикатор качества соединения и reconnect.
- HUD остается в screen space и не проходит world culling.

### Смерть и spectator mode

После серверного события смерти:

- немедленно отключи отправку игровых input;
- проиграй смерть и покажи overlay без перекрытия всего наблюдения;
- переключи камеру на живого игрока;
- добавь кнопки переключения между живыми игроками и общий обзор, если он не требует рисовать всю карту;
- продолжай показывать HUD, таймер и счет;
- не показывай кнопку возрождения.

Обычный зритель получает те же возможности. Если backend повысил его роль для следующего раунда, покажи уведомление «Вы играете в следующем раунде».

### Результаты

- Победитель или сообщение «Раунд без победителя».
- Причина завершения.
- Таблица: артефакты, PvP kills, monster kills, оставшийся HP, состояние.
- Countdown до следующего раунда.
- Название следующей карты показывай только после подтверждения backend.

## Управление

Поддержи клавиатуру:

- `A` / `←` — влево;
- `D` / `→` — вправо;
- `W`, `↑` или `Space` — прыжок;
- `J` или `X` — атака;
- `Tab` — временная таблица игроков;
- `Esc` — только UI-меню, без остановки серверной игры.

Не отправляй одно WebSocket-сообщение на каждый browser key event. Храни состояние кнопок, присваивай input sequence number и отправляй с ограниченной частотой, согласованной с backend. Не допускай browser key repeat для повторного запуска одноразового jump/attack без release edge или серверного cooldown.

## Сетевая синхронизация

Реализуй отдельный network client со следующими обязанностями:

- connect/resume/disconnect;
- versioned JSON protocol;
- автоматический reconnect с backoff и верхним пределом попыток;
- безопасное хранение session token на время сессии;
- валидация формы входящих сообщений;
- маршрутизация reliable events и snapshots;
- latency estimation;
- отбрасывание сообщений старого `roundID` и устаревших snapshots;
- защита UI от duplicate events.

### Локальный игрок

Используй ограниченный client-side prediction для движения локального персонажа, если это совместимо с существующим renderer:

- сразу применяй собственный input к локальному представлению;
- храни небольшой буфер неподтвержденных inputs;
- по `lastProcessedInputSeq` удаляй подтвержденные inputs;
- выполняй reconciliation от authoritative position;
- небольшие расхождения сглаживай, большие исправляй быстро;
- HP, сбор, попадания, смерть и победа всегда применяются только по данным сервера.

Если prediction существенно мешает первой рабочей версии, сначала обеспечь чистое authoritative движение и изолируй слой так, чтобы prediction можно было включить без переписывания scene.

### Другие сущности

- Удаленных игроков и монстров показывай с interpolation buffer примерно 100–150 мс, значение сделай настраиваемым.
- Не экстраполируй надолго при потере snapshots.
- Артефакты и события смерти переключай по серверным событиям; snapshot служит восстановлением истины.
- При reconnect запроси/прими полный current state и пересоздай scene idempotently.

## Игровая сцена

Раздели ответственность:

- app/UI layer — формы, overlay, HUD, results и connection status;
- game scene — camera, world, entities, animation и local visual prediction;
- map renderer — построение geometry, chunks и viewport culling;
- entity views — player, monster, collectible, effects;
- input controller — клавиатура и формирование input state;
- network client — WebSocket и reconnect;
- state adapters/store — преобразование protocol DTO в удобное client state.

Не привязывай WebSocket callbacks напрямую к созданию и уничтожению sprites. Сообщения сначала нормализуются в состояние/события, а scene синхронизирует view контролируемым способом.

## Отрисовка

- Используй внутреннюю игровую систему координат и responsive canvas.
- Камера следует за локальным игроком с умеренным lerp/dead zone, но не выходит за world bounds.
- Для spectator camera следуй за выбранным игроком.
- Имена и HP-bars привязаны к персонажам, но масштаб текста остается читаемым.
- Имя экранируется и не вставляется через небезопасный HTML.
- Платформы, hazard-зоны, артефакты и монстры визуально различимы даже с placeholder graphics.
- Четыре player colors должны различаться и не полагаться только на красный/зеленый; добавь дополнительный символ или силуэт для доступности.
- Не запускай тяжелые анимации offscreen.
- Не обновляй DOM на каждый snapshot для всех координат: игровые позиции остаются внутри renderer, а UI-store получает только данные HUD с разумным throttling.

## Анимационные состояния

Поддержи минимум:

- player: `idle`, `run`, `jump`, `fall`, `attack`, `hurt`, `dead`;
- monster: `idle`, `walk`, `attack`, `hurt`, `dead`;
- collectible: idle-пульсация и подтвержденное исчезновение;
- effects: hit flash, damage number, pickup `+1`, round winner effect.

Анимация атаки клиента не означает попадание. Попадание и damage effect запускаются только по серверному событию.

## Ошибки и reconnect

Показывай состояния:

- подключено;
- нестабильное соединение;
- переподключение;
- соединение потеряно;
- сессия истекла.

Во время reconnect:

- прекрати отправку input;
- не позволяй локальному персонажу визуально продолжать бесконечное движение;
- сохрани интерфейс наблюдения в замороженном/затемненном состоянии;
- после успешного resume примени полный snapshot и authoritative role;
- после отказа resume верни пользователя на экран подключения с понятным сообщением.

## Производительность

Цель для обычного desktop-браузера:

- 60 FPS в renderer при типичном раунде;
- отсутствие полной перерисовки React/Vue/Svelte-дерева на каждый snapshot;
- число визуальных объектов зависит от render window, а не от полной площади карты;
- cleanup всех scene listeners, timers, WebSocket subscriptions и entities при смене карты/unmount;
- один canvas и один активный game loop;
- production build без debug overlays по умолчанию.

Добавь dev-only счетчики FPS, visible/total entities, active chunks и snapshot rate. Не занимайся преждевременной микрооптимизацией, но viewport windowing является обязательным функциональным требованием.

- Не коммить секреты и реальные токены.

## Критерии готовности

Работа завершена, когда:

- приложение запускается из `./frontend` документированной командой;
- пользователь вводит имя и подключается;
- показывается authoritative active/spectator role и очередь;
- отображаются все пять server-provided map definitions;
- камера показывает только часть большой карты и следует за игроком;
- viewport culling/windowing подтверждается debug overlay и тестами;
- полный мир не отрисовывается каждый кадр;
- отображаются имена, HP, счет `N/5`, монстры и артефакты;
- управление отправляет sequence inputs, а не координаты;
- локальное движение не ломается при server reconciliation;
- удаленные игроки и монстры интерполируются;
- атака визуализируется, но урон применяется только по серверу;
- после смерти управление выключается и включается spectator camera;
- пятый подтвержденный артефакт приводит к серверному экрану победителя;
- после intermission старая scene корректно очищается и загружается новая карта;
- reconnect не создает дублирующиеся listeners/entities;
- линтер, тесты и production build проходят;
- README описывает стек, renderer, windowing, протокол, управление и запуск.
